
Shipping is restored and independently verified.

**What was wrong:** the `shipping` Deployment's `QUOTE_ADDR` env var had been changed to `quote:0000` — not a resolvable URL for the `quote` dependency. Shipping's own logs showed the consequences directly: the new pod logged `Requesting quote quote_service_addr="quote:0000/getquote"` and never produced a `Sending Quote`, while the pod that had served healthily for 18 h before the incident logged `http://quote:8080/getquote` → `Sending Quote` → `Tracking ID Created`.

**Repair:** one env value, restored to `http://quote:8080`.

Two details worth calling out, since a partial fix would have left the service broken:
- My first patch set `quote:8080` (port fixed, scheme missing). Verification caught it: the pod logged `quote:8080/getquote` and still produced no `Sending Quote`, because this app appends `/getquote` to the raw value and a schemeless value is not a valid URL. The value must carry `http://` — exactly what the pre-incident pod logged.
- I checked the whole object, not just the symptom: no `nodeSelector`/`affinity`/`tolerations` were added, and the rollout landed on ReplicaSet `shipping-5bc6f87785` — the *same* pod-template hash as the ReplicaSet that served before the incident, i.e. the entire pod template is now byte-identical to the pre-incident one. The `wait-for-flagd` init container is chart-normal (peers carry `wait-for-kafka` / `wait-for-astronomy-db`), and no Service selector, port, HPA, quota, LimitRange or NetworkPolicy is involved.

The remaining Warning events (`checkout` `hello-bench-arm64` ImagePullBackOff, a `frontend` probe failure) reference pods that no longer exist; both those workloads are currently 1/1 Ready with healthy endpoints and are unrelated to shipping.
