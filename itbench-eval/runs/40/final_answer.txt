
Service is restored and verified. Summary:

**Root cause:** The running `valkey-cart` process had its maxmemory lowered at runtime — at 04:13:40 UTC a one-off Job (`valkey-cart-init`, created 04:13:27, container `valkey-cli`, pod logs `OK\nOK\n`) issued `CONFIG SET maxmemory 1048576` (1 MiB) on the live server. The valkey log recorded it verbatim: `WARNING: the new maxmemory value set via CONFIG SET (1048576) is smaller than the current memory usage (1408632)`. With the effective policy non-evicting, valkey rejected every write with `OOM command not allowed when used memory > 'maxmemory'`, which the cart service surfaced as `FailedPrecondition: Can't access cart storage` and the frontend as HTTP 500 on `POST /api/cart`. Reads kept returning 200, which is why the workload still looked "Running" and the endpoint was "ready".

**Why the spec was not the fault:** the same pod template had been serving successful writes (RDB saves every 300s, "100 changes") for 17h, and the server itself logged the change as arriving "via CONFIG SET", not from startup configuration. The override existed only in the running process, so recreating the pod from the unchanged Deployment restored the declared configuration.

**Fix applied (one change):** `change-executor` performed a rollout restart of `deployment/valkey-cart`; old pod `valkey-cart-6d56fb7ccc-zw2kb` was replaced by `valkey-cart-8bd97844d-z69jw`.

**Verification (re-read after the change):**
- New valkey pod: `Phase: Running`, `Ready/ContainersReady: True`, 0 restarts; log `Ready to accept connections tcp`; Deployment `1/1 ready/available`.
- `valkey-cart` Service endpoint: `1 ready / 0 not-ready`.
- Cart service logs: continuous `AddItemAsync`/`GetCartAsync`/`EmptyCartAsync` with **no** `FailedPrecondition` error lines (previously the dominant symptom).
- Frontend logs: `POST /api/cart` now `http.response.status_code: 200` (it was 500 with the OOM stack trace before).
- Warning events: no new warnings; the only ones are stale `FailedScheduling` entries for other pods.

Note (not changed): the valkey container runs with no maxmemory/eviction args declared, under a 20Mi memory limit. That is the pre-existing chart state and unrelated to this incident; adding `--maxmemory 20mb --maxmemory-policy allkeys-lru` would be a reasonable future hardening but was out of scope for the smallest fix.
