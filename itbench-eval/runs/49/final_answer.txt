
**Service restored.** Summary of the incident and the repair:

**What was wrong.** The `frontend` Deployment in `test-agent` carried a `readinessProbe` on the container pointing at **port 40** (`httpGet /ready`). Nothing listens there — the app serves on 8080 — so the ReplicaSet created by that change could never mark its pod Ready. The rollout stalled (`frontend-86688f6f56` pod stuck `ContainerCreating`/Running-but-unready, `Readiness probe failed: dial tcp ...:40: connection refused`), leaving the `frontend` Service with a not-ready endpoint (degraded), while callers through `frontend-proxy` saw errors.

**Why it was a fault, not configuration.** I confirmed against the Helm-rendered original (`otel-demo`, chart `opentelemetry-demo-0.42.3`) by reading the manifest myself: the chart's `frontend` Deployment has **no** probes — the container goes `image → ports → env → resources → securityContext`. A namespace probe audit confirmed `frontend` was the *only* workload with a readiness probe (all 24 others have none), so it had been added by the incident, not by configuration. It was the sole deviation from the chart on that object — image, ports, env, resources, securityContext, serviceAccount and the absence of nodeSelector/affinity/tolerations/initContainers all matched.

**Repair.** Removed the injected `readinessProbe` (single-field patch, nothing else touched), restoring the object to its pre-incident state.

**Proof of restoration.** The Deployment rolled back onto ReplicaSet `frontend-6f68f54c79` — the *same* ReplicaSet/pod that existed before the change — which proves the restored pod template is byte-identical to the pre-incident template (no other injected field remains). Deployment is `1/1 ready, 1 available, Progressing/Available: True`; the `frontend` Service now shows `1 ready / 0 not-ready`; no new warning events (the only `Unhealthy` event is the historical one on the now-deleted pod); the pod is `Ready: True, 0 restarts` and its access logs show live `200` responses on `/api/*`.

One honest note: the `load-generator` browser user logs a continuous stream of `503 Service Unavailable` console messages. That is not the frontend: the frontend serves `200`s live, all 24 Services have healthy endpoints, and `grafana`/`jaeger`/`opensearch`/`prometheus`/`firepit` are deliberately disabled in this release's values while `frontend-proxy` still has routes for them — an environment-level, pre-existing condition unrelated to the fault I repaired.
