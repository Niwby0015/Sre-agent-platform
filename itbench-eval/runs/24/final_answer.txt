
Service restored and verified.

**Root cause:** The `checkout` Deployment's container env `KAFKA_ADDR` was set to `kafka:9999`, but the `kafka` Service only listens on `9092`/`9093`. The checkout app's Kafka producer therefore failed on every `PlaceOrder`, surfacing errors to callers — while the pod itself stayed `Ready` (no probes, lazy producer connect), so the breakage was silent from the pod's perspective.

**Evidence used:**
- Live peer `Deployment/accounting` (same Helm chart, untouched revision 1) uses `KAFKA_ADDR=kafka:9092`.
- `Service/kafka` exposes only `9092`/`9093`; otel-collector config also uses `kafka:9092`.
- checkout's own `wait-for-kafka` init container probes `kafka 9092` (and succeeded) — so 9999 contradicts the chart's own assumptions.
- No other divergence found: image `ghcr.nju.edu.cn/open-telemetry/demo:3.1.0-checkout` correct, no stray nodeSelector/affinity/tolerations, no NetworkPolicies, no Helm override.

**Fix:** single-field patch of `KAFKA_ADDR` → `kafka:9092` (nothing else touched).

**Verification:** Re-read `Deployment/checkout` — now revision 38 with `KAFKA_ADDR=kafka:9092`, image/limits/init container/volumes unchanged and no scheduling constraint added. New pod `checkout-5d89dfbfff-mqwmz`: `Initialized/Ready/ContainersReady=True`, 0 restarts; `Service/checkout` endpoints 1 ready / 0 not-ready; no new warning events (remaining warnings are stale, from the earlier out-of-band bad-image ReplicaSet).
