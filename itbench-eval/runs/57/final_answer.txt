
Service restored and verified.

## What was wrong

The `checkout` Deployment had been mutated out-of-band (its Helm release `otel-demo` still renders the clean spec — `helm get manifest` shows the correct image and **no** nodeSelector). Two fields had drifted together:

1. **Image:** `quay.io/it-bench/hello-bench-arm64:2.0.0` instead of `ghcr.nju.edu.cn/open-telemetry/demo:3.1.0-checkout`. The pull failed with `no match for platform` (that image has no matching arch manifest for the node) — every pod of ReplicaSet `checkout-69d7c967bc` went `ErrImagePull`/`ImagePullBackOff` (4 successive pods: `clgg2`, `zlxh5`, `2qz2r`, `77wkp`). Because `maxUnavailable: 25%` rounds down against `replicas: 1`, the rollout could never evict the last good pod, so the Deployment sat stuck at `READY 0/1` while thrashing.
2. **Scheduling constraint:** `nodeSelector: {kubernetes.io/hostname: node1}` — added to the same template, not in the Helm manifest, and not present on any sibling component. This is exactly the "works but isn't the original configuration" kind of leftover; it disappeared as soon as the image was fixed because the identical old ReplicaSet was reused, so it would have been easy to leave behind silently.

Sibling deployments confirmed the conventions: `ghcr.nju.edu.cn/open-telemetry/demo:3.1.0-<component>` with no nodeSelector (the `wait-for-*` init container is chart standard — `cart` has the same pattern, and it appears in the Helm manifest, so it was left alone).

## Fix applied

One patch to `deployment/checkout` restoring the image and removing `nodeSelector` (revision 31 → 32). Nothing deleted, recreated, scaled or silenced; nothing outside `test-agent`, and nothing else in the namespace touched.
